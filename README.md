Проект разделен на исходный код (`src/`) и директорию с данными (`data/`).

```text

├── docker-compose.yml

│   ├── api/                    # FastAPI сервер и веб-интерфейс

│   │   ├── evaluation.py       # Оффлайн A/B тестирование метрик
│   │   ├── formulas.py         # Формулы расчета баллов
│   │   ├── metrics.py          # Функции Precision, NDCG, MRR...
```

> **ВАЖНО: Загрузка исходных данных**
> Таблицы с сырыми данными (CSV-файлы) не включены в репозиторий. Пользователь должен самостоятельно поместить выгрузки в папку `data/` перед запуском проекта. Названия файлов и структура папок (особенно `data/customers-actions/`) должны строго соответствовать примеру выше. ## Как запустить и воспроизвести результат

### 1. Требования

- **Docker** (для запуска сервера Meilisearch)
- **Python 3.9+**

### 2. Подготовка

Клонируйте репозиторий и перейдите в папку проекта:

```bash
git clone https://github.com/EnikeevAnton/milis-personal-index.git
cd milis-personal-index
```

Создайте `.env` на основе примера:

```bash
cp .env.example .env
```

### 3. Запуск Meilisearch
Поднимите контейнер:
```bash
docker compose up --build -d
```

### 4. Установка зависимостей Python

Создайте и активируйте виртуальное окружение, а затем установите необходимые библиотеки:

Для Linux/macOS:
```bash
python -m venv venv
source venv/bin/activate
pip install -r requirements.txt
```
Для Windows:

```Bash
python -m venv venv
venv\Scripts\activate
pip install -r requirements.txt
```
### 5. Запуск pipeline
Главный скрипт последовательно выполнит следующие действия:
- загрузит данные из таблиц и подготовит их
- добавит данные в индекс
- рассчитает скоры

```bash
python src/main.py
```
Вы можете проверить загруженные данные и рассчитанные скоры в интерфейсе Meilisearch по адресу http://localhost:7700 (Master Key берется из .env).

### 6. Проверка работы API (Целевые сценарии)
Вместо прямых запросов к базе, мы подготовили FastAPI-сервер с набором готовых инструментов:

**Доступные эндпоинты (API):**
* **`GET /api/v1/search/recommend`** — Универсальная выдача товаров витрины с поддержкой сортировок, фильтров Meilisearch и автоматическим разрешением ничьих.
* **`GET /api/v1/analytics/evaluate`** — Запуск Time-Split валидации алгоритмов с расчетом метрик качества (Precision, NDCG, Revenue Recall).
* **`POST /api/v1/admin/scoring/recalculate`** — Принудительный фоновый пересчет скоров на основе истории логов.
* **`POST /api/v1/admin/pipeline/trigger`** — Запуск полного пайплайна в фоне (сборка ETL -> переиндексация -> пересчет скоров).

Для запуска API выполните:

```Bash
uvicorn src.api.server:app --reload
```
После запуска откройте в браузере интерактивную документацию Swagger UI: http://127.0.0.1:8000/docs.

### 7. Оценка качества ранжирования (Оффлайн метрики)

Для оффлайн тестирования алгоритмов (через эндпоинт `GET /api/v1/analytics/evaluate`) реализованы классические метрики информационного поиска. Расчет производится изолированным модулем `src/engine/metrics.py`.

#### Методология Time-Split валидации
Чтобы честно оценить, насколько хорошо математическая формула предсказывает **будущий спрос**, система не должна «подглядывать» вперед. Для этого симулируется перенос в прошлое с помощью сплита по времени (Time-Split):

1. **Разделение временной шкалы на 3 интервала:**
   * **`target_date`** (Настоящее) — самая последняя (верхняя) точка в массиве логов.
   * **`split_date`** (Точка сплита) = `target_date - test_days` (отсекаем, например, последние 7 дней для проверки).
   * **`start_date`** (Начало истории) = `split_date - history_days` (берем, например, 30 дней обучающей истории до сплита).

2. **Формирование прогноза (Train / Взгляд в прошлое):**
   * Алгоритм «замораживает» состояние системы на момент `split_date`.
   * В обучающий сплит попадают действия (просмотры, добавления в корзину, покупки), произошедшие строго в интервале `[start_date, split_date]`.
   * Для каждого товара рассчитываются итоговые баллы (`popularity`, `novelty`, `commercial_score`), при этом возраст события для экспоненциального затухания рассчитывается строго относительно точки сплита:
     ```python
     age_days = max(0, (split_date - day_dt).days)
     ```

   * Товары сортируются по убыванию рассчитанного балла, отбирается **Топ-K кандидатов** (по умолчанию $K=30$) — это наш **Прогноз (Prediction)**.

3. **Сбор фактов (Test / Ground Truth / Взгляд в будущее):**
   * Открываются скрытые дни тестового периода `(split_date, target_date]`.
   * Формулы скоринга к этим данным **не применяются**. Система собирает чистые фактические результаты взаимодействия: просмотры (`views`), добавления в корзину (`carts`), количество выкупленных штук (`purchases`) и итоговую кассу (`revenue`).

---

#### Подробное описание метрик и математические формулы

Сформированный Топ-K кандидатов сверяется с фактическим поведением покупателей из тестового сплита.

##### Что такое «выдача» и «позиция товара»?
Перед разбором формул важно зафиксировать базовые понятия:
* **Выдача (рекомендательный список)** — это итоговый упорядоченный список из $K$ товаров (например, Топ-30), который наш алгоритм построил на основе обучающей истории, отсортировав товары по убыванию их прогнозного балла.
* **Позиция ($pos$ или $rank$)** — это конкретное порядковое место товара в этом списке: 1-е место (самый верх выдачи), 2-е место, ..., 30-е место (конец первой страницы).

Поведение покупателей устроено так, что верхние позиции получают максимум внимания, а до конца списка доходят не все. Метрики ранжирования учитывают этот фактор по-разному.

---

##### Precision@K (Точность)
* **Что показывает:** Какая доля из предложенных нами $K$ товаров действительно оказалась релевантна покупателям в будущем. Позиция товара внутри списка здесь **не учитывается** — важно лишь само попадание на первую страницу.
* **Критерий релевантности (Ground Truth):** Товар считается успешным (Hit), если в тестовом периоде у него был хотя бы один просмотр, добавление в корзину или покупка (`views > 0 OR carts > 0 OR purchases > 0`).
* **Формула:**

  $$\text{Precision@K} = \frac{|\text{Recommended}_{1..K} \cap \text{ActualRelSet}|}{K}$$

* **Бизнес-смысл:** Отражает общую чистоту первой страницы выдачи. Если из 30 предложенных товаров пользователи взаимодействовали только с 3, точность равна 10%.

##### NDCG@K (Normalized Discounted Cumulative Gain)
* **Что показывает:** Идеальность порядка выдачи с учётом коммерческой успешности каждого товара. Метрика требует, чтобы лидеры продаж занимали самые верхние позиции.
* **Вес релевантности (Gain):** В качестве веса используется **фактическое количество выкупленных штук** (`purchases`) в тестовом окне. Просмотры и добавления в корзину здесь не учитываются.
* **Влияние позиции:** Знаменатель $\log_2(pos + 1)$ работает как штраф за дальность. На 1-й позиции штрафа нет ($\log_2(1+1)=1$), а на 7-й строчке ценность покупок разделится уже на $\log_2(7+1)=3$. Если алгоритм поставит самый продаваемый товар вниз списка, итоговый балл сильно упадет.
* **Формула:**

  $$\text{NDCG@K} = \frac{\text{DCG@K}}{\text{IDCG@K}}$$

  $$\text{DCG@K} = \sum_{pos=1}^{K} \frac{\text{Purchases}_{pos}}{\log_2(pos + 1)}$$

  *Где **IDCG@K** — это максимально возможный **DCG**, рассчитываемый путем идеальной сортировки тестовых покупок по убыванию.*
* **Бизнес-смысл:** Гарантирует, что абсолютные хиты продаж находятся на самых привлекательных для покупателя строчках.

##### MAP@K (Mean Average Precision)
* **Что показывает:** Усредненную точность выдачи на всех строчках, где встретился релевантный товар. Оценивает кучность и стабильность полезных товаров в верхней части списка.
* **Влияние позиции:** Метрика рассчитывает промежуточную точность ($\text{Precision@pos}$) накопительным итогом сверху вниз. Если первый успешный товар стоит на 1-м месте, он дает точность $1/1=1.0$. Если второй успешный товар стоит на 5-м месте, на этом шаге точность составит $2/5=0.4$. Итоговый результат усредняется. Чем ближе к началу списка сгруппированы релевантные товары, тем выше итоговый балл.
* **Формула:**

  $$\text{MAP@K} = \frac{1}{\min(K, |\text{ActualRelSet}|)} \sum_{pos=1}^{K} \left( \text{Precision@pos} \cdot \mathbb{I}(\text{item}_{pos} \in \text{ActualRelSet}) \right)$$

  *Где **I** — индикаторная функция (1, если товар на строчке **pos** успешен, иначе 0).*
* **Бизнес-смысл:** Строго наказывает систему за неудачный порядок. Алгоритм получит значительно меньший балл, если первый полезный товар встретится покупателю на 20-й строчке, а не на 1-й.

##### Quantity / Revenue Recall@K (Коммерческая полнота)
* **Что показывает:** Какую долю от общих будущих продаж магазина покрывают товары, выведенные нашим алгоритмом в Топ-K. Позиция товара внутри списка здесь не учитывается (как и в Precision).
* **Взвешивание (Weights):**
  * Для **Quantity Recall** суммируются проданные штуки (`purchases`).
  * Для **Revenue Recall** суммируется сгенерированная выручка (`revenue`).
* **Формула:**

```math
\mathrm{Recall}@K = \frac{\sum_{\text{item} \in \text{TopK}} \mathrm{Weight}_{\text{item}}}{\sum_{\text{item} \in \text{Catalog}} \mathrm{Weight}_{\text{item}}}
```


* **Бизнес-смысл:** Ключевой финансовый показатель алгоритма. Значение $\text{Revenue Recall@30} = 0.15$ означает, что отранжировав витрину по данной формуле, мы сразу помещаем на первую страницу товары, которые сгенерируют 15% всей будущей кассы магазина.

##### MRR@K (Mean Reciprocal Rank)
* **Что показывает:** Насколько высоко в выдаче находится самый первый релевантный товар.
* **Влияние позиции:** Оценка зависит исключительно от порядкового места первого успешного товара (**rank** первого попадания). Если клиент кликнет на товар с 1-й строчки, балл равен $1/1=1.0$. Если первый заинтересовавший товар оказался на 4-й строчке — балл составит $1/4=0.25$.
* **Формула:**

  $$\mathrm{MRR}@K = \frac{1}{\mathrm{rank}_{\text{first hit}}}$$

  *Если в Топ-**K** нет ни одного успешного товара, **MRR@K = 0.0**.*
* **Бизнес-смысл:** Метрика быстроты и удобства. Отражает вероятность того, что клиент сразу увидит привлекательный товар на первом экране без необходимости скроллить страницу.
